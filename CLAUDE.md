# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is **frans-app**, the Angular (v21, zoneless) frontend for a committee/community app ("Franciscus"). It's one of two repos for this project — the other is a separate .NET backend API (`FransApi`, hosted at `franciscus-api.stanenmennocomite.nl`) that this repo has no direct access to. When backend behavior needs to change, that's out of scope here; this repo only consumes the API via the generated client described below.

Features live under `src/app/modules/`: `login`, `home`, `soundboard`, `wheel-of-fortune`, `admin`, `liedjes`, `poop-app`.

## Commands

Package manager is **pnpm** (`pnpm-lock.yaml` is present — use `pnpm install`, not npm/yarn).

- `ng serve` / `npm start` — dev server at `http://localhost:4200/`, using `environment.ts` (points at `https://localhost:7225`, i.e. a locally running FransApi backend).
- `ng build` — production build (uses `environment.prod.ts`, service worker enabled).
- `ng test` — Karma/Jasmine unit tests. Run a single spec by passing a filter through Karma, e.g. `ng test --include='**/auth-service.spec.ts'`.
- `ng lint` — ESLint (`eslint.config.js`, flat config, `angular-eslint` + `@stylistic`).
- `npm run deploy` (`ng deploy --base-href=/Franciscus/`) — builds and force-pushes `dist/` to the `gh-pages` branch via `angular-cli-ghpages`, which is what GitHub Pages actually serves. **Never run this yourself unless the user explicitly asks you to deploy** — treat it the same as a push to a live environment.

There is no CI workflow in this repo (`.github/workflows` doesn't exist) — going live is always this manual `deploy` step, not an automatic side effect of pushing to `master`.

## Architecture

**Routing & hosting**: `app.routes.ts` uses `provideRouter(routes, withHashLocation())` — hash-based routing is required because the app is served from a GitHub Pages subpath (`/Franciscus/`) via the `gh-pages` branch, not a server that can rewrite arbitrary paths.

**Feature module pattern**: most routed features pair a standalone component (e.g. `home.ts`) with a same-folder `*.module.ts` that only exists to declare/import that component's dependencies (Angular Material modules, etc.) and is attached via the route's `providers:` array (see `app.routes.ts`). Some newer routes (`admin`) skip this and use plain `loadComponent`. When adding a feature, check whether it needs its own Angular Material imports before deciding which pattern to copy.

**Auth is two-layered**:
1. Firebase Auth (`@angular/fire`) is used only to sign in with Google and obtain an ID token — it is not the app's actual session.
2. That Google ID token is exchanged with the FransApi backend (`AuthService.handleGoogleLogin` → `_api.auth(idToken)`) for the app's own `authToken`/`refreshToken` pair, stored in `localStorage`. All authenticated API calls use this pair, not Firebase's session.

`auth-interceptor.ts` attaches the bearer token to outgoing requests, decodes JWT expiry client-side (`jwt-decode`), and transparently calls `authRefresh` when the access token (but not the refresh token) has expired. `auth-guard.ts` and `admin-auth-guard.ts` gate routes on `AuthService.isInitialized`/`user()`; admin access is `user().role !== 0`.

**Generated API client**: `src/app/apiclients/fransapi.client.ts` is generated by NSwag from the backend's OpenAPI spec, configured in `src/app/apiclients/api.client.nswag` (points at `https://localhost:7225/swagger/v1/swagger.json` — the backend must be running locally to regenerate). Do not hand-edit this file; regenerate it via NSwag when the backend API shape changes. The base URL is injected via the `FRANS_API_BASE_URL` token, wired to `environment.apiUrl` in `app.config.ts`.

**Environments**: `environment.ts` (dev, local backend) and `environment.prod.ts` (prod, live backend) both also carry the shared Firebase project config — Firebase project is the same across environments, only the FransApi `apiUrl` differs.

**PWA**: service worker (`ngsw-config.json`) is enabled only outside dev mode (`app.config.ts`), registered with a 30s stability delay.

**`liedjes` module** (kamp-feitjes per kind, later used to write camp songs): follows the **admin** pattern (standalone components + `loadComponent`, no `.module.ts`). `liedjes.ts` is the overview grid (`/liedjes`), `child-detail.ts` is a single child's page with its facts list (`/liedjes/:id`) — both behind the plain `authGuard` (any logged-in user, no admin restriction, matching the backend's permission model for this feature). `liedjes-api.ts` wraps the generated client the same way `admin-api.ts` does.

Child profile pictures are uploaded to the .NET API and the API returns a **relative** path (e.g. `/uploads/children/{guid}.jpg`) — unlike a user's Google profile picture, which is already an absolute URL. Any `<img>` showing a child's photo must prefix that path with `environment.apiUrl` (see `photoUrl()` in `liedjes.ts`/`child-detail.ts`); forgetting the prefix is the most likely bug if this ever looks broken.

`AppCard` (`home.ts`) supports an optional `icon` (Material icon name) as an alternative to `image`, rendered by `home.html`, for tiles that don't have (or don't need) a dedicated PNG asset — used by the "Liedjes" tile.

**Per-app access gating applies to every app now** (Soundboard, Rad, Liedjes, Top Secret) — not just the poop-app it started with. `AppCard` supports `requiresAppKey`, set on all four tiles in `home.ts`; the `visibleApps` computed signal filters a tile out unless `user()?.grantedApps` (from the backend's `User.grantedApps`) contains that key. This is **UI convenience only**; the actual enforcement is the backend's `[RequireAppAccess]` filter on the corresponding controller — never rely on hiding the tile as the real security boundary. `core/auth/app-access-guard.ts` exports a **factory** `appAccessGuard(appKey)` (not a single fixed guard) used on every gated route alongside `authGuard`, e.g. `canActivate: [authGuard, appAccessGuard('soundboard')]`.

**No automatic backfill when a new app gets gated.** When Soundboard/Rad/Liedjes were added to this system, nobody's existing access carried over on purpose — every user (including the admin) had to be re-granted access per app via the admin UI after deploying. If an app ever stops working right after a deploy and the fix is "nobody has access", that's expected, not a bug — check `/admin`'s per-user "App-toegang" menu item first.

**Push subscriptions are centralized in `core/push/push-notification-service.ts`** (`PushNotificationService`), not owned by the `poop-app` module — both the home screen's opt-in prompt and the poop-app page's own controls share this one subscribe path. It exposes `permissionGranted`/`permissionDenied` signals (derived from `Notification.permission`, not from whether a subscribe call has ever succeeded) and two methods: `subscribe()` (requests permission if needed, via Angular's built-in `SwPush` + `environment.vapidPublicKey`, then posts the subscription to the API's `/push/subscribe`) and `refreshIfAlreadyGranted()` (silently re-subscribes, once per app load, only when permission is already granted — see below for why). **Web Push notifications on iOS only work if the PWA has been "Added to Home Screen"** — plain Safari tabs can't receive them (iOS 16.4+ requirement), keep this in mind if push "doesn't work" during testing on an iPhone. `environment.prod.ts`'s `vapidPublicKey` must match whatever private key is configured on the Pi (see the API repo's `CLAUDE.md`) — dev and prod intentionally use different VAPID keypairs.

**Push subscriptions can go silently stale, with no error anywhere** — the server and Apple's push relay both report success even though the notification never reaches the device (confirmed by reproducing it with a completely independent library, ruling out a bug in our own send code). There's no reliable signal from the browser when this happens: the standard `pushsubscriptionchange` event that's supposed to fire when a push service invalidates a subscription isn't dependable on Safari/iOS, and even `Notification.permission` itself can't always be trusted to update promptly — `PushNotificationService` re-reads it on every `visibilitychange` (there's no cross-browser "permission changed in OS settings" event) rather than only once at construction. The practical mitigation, not a full fix: `App`'s constructor (`app.ts`) runs an `effect()` that calls `PushNotificationService.refreshIfAlreadyGranted()` once per app load for anyone with `poop-app` access who already granted permission — cheap and idempotent, since re-subscribing when already granted doesn't re-prompt. `home.ts`'s `showNotificationPrompt` (a small banner above the app tiles, only for users with `poop-app` access) is the *first* ask; `poop-app.ts`'s "Vernieuw abonnement" button is the manual fallback for forcing a fresh subscription on demand, since the initial "enable" button disappears once permission is already granted. **Gotcha**: `showNotificationPrompt`'s condition has to special-case a just-failed attempt — hiding the banner whenever permission is `'denied'` (normally correct, since the browser won't prompt again) would also hide the error message a failed `subscribe()` call just set, at the exact moment it's supposed to be shown; it stays visible whenever there's a pending `notificationError`, denied or not. See the API repo's `CLAUDE.md` for the full push-delivery incident story (also covers the `notification`-wrapper payload gotcha).

**`poop-app.ts` is the actual "Poeplog" feature** (home tile and page title both say "Poeplog", not "Top Secret" — that name is gone from the codebase entirely). A WhatsApp-style chat feed (`.chat-bubble`, right-aligned/green via `.mine` for your own entries, left-aligned/white with a sender-name line for everyone else's) shows every logged "hij heeft gepoept 💩"/"hij heeft geplast 💦" event, fetched from `GET /poop-app/log` on init; two large buttons at the bottom (`logPoop()`/`logPee()`) call `POST /poop-app/log`, which both appends to the local `log` signal and — server-side — pushes a notification to everyone else (not yourself; see the API repo's `CLAUDE.md`). `PoopLogType` is generated by NSwag as a plain `0 | 1` union type, not a real TS enum (same as the existing `RoleType`), hence the local `POOP_LOG_TYPE_POOP`/`POOP_LOG_TYPE_PEE` constants instead of referencing enum members. Note: `PoopLogEntry.createdAt` comes back from NSwag as a `dayjs.Dayjs`, not a native `Date` — format it with `dayjs(...).format(...)` like `child-detail.ts` already does, not Angular's `date` pipe (which expects a real `Date`). The original `sendTestNotification()` push-delivery diagnostic (5-second countdown, `<details>` section) has been removed along with its backend endpoint now that the real logging flow itself proves push delivery works. `clearLog()` (a "Log wissen" button, only rendered when `isAdmin()` — `user()?.role === 0`, same check as `admin-auth-guard.ts`) opens an inline `ConfirmClearLogDialog` (defined right in `poop-app.ts`, same "small dialog next to its one usage" pattern as `admin.ts`'s `ConfirmDeleteDialog`) before calling `DELETE /poop-app/log`; there's no undo. Each bubble also gets its own small `deleteEntry(id)` (×) button whenever `canDelete` (your own entry, or any entry if you're admin) — deliberately **no** confirmation dialog there, unlike clearing the whole log, since undoing a single misclick is low-stakes and instantly redone by just logging again.

**Managing app access is per-person, not per-app**: each `.user-card` in `admin.html` has a single overflow menu (`mat-menu`, "Bewerken"/"App-toegang"/"Verwijderen") rather than separate always-visible icon buttons — this replaced an earlier design with a floating per-app button, which didn't scale UX-wise once you think in terms of "what can this person access" rather than "who can access this one app". `app-access-dialog.ts`'s `GATEABLE_APPS` constant (currently `soundboard`/`wheel`/`liedjes`/`poop-app`) is the single place to add a new app to the toggle list when something else becomes access-gated later — the dialog itself and the backend's `AppAccess`/`RequireAppAccess` are already generic per-app.

**Soundboard no longer uses Firebase Storage.** It used to upload/list/delete sound files directly via `@angular/fire/storage`; that had its own, separate access-control model unrelated to `AppAccess` (a Firebase Storage security rule, not a `RequireAppAccess` check), which was confusing — "you don't have soundboard access" could mean two different things depending on which system was actually blocking you. `SoundService` now calls the API's `/sounds` endpoints instead (same disk-backed pattern as Liedjes' child photos), so Soundboard access is enforced the same way as every other app. The one-time migration of pre-existing sounds is complete — the migration dialog, its admin trigger button, the backend's `migrate-batch` endpoint, and the `provideStorage`/`@angular/fire/storage` registration in `app.config.ts` have all been removed. Firebase (`@angular/fire`) is now used only for Auth (Google sign-in) — nothing in this repo touches Firebase Storage anymore.

**Gotcha: `mat-checkbox` label contrast inside dialogs.** The app forces `--mat-sys-on-surface` to white globally (for the green page shell), and `mat-checkbox`'s label (`.mdc-label`) uses that token directly rather than just inheriting `color` — so a plain `mat-checkbox { color: ... }` override in a dialog's component styles does *not* reach it (Angular's view encapsulation scopes it to the wrong element, since `.mdc-label` lives inside `mat-checkbox`'s own template). Needs `:host ::ng-deep .mdc-label { color: ...; }` to actually land. If a checkbox (or likely other MDC form controls) ever looks washed-out/invisible inside a light dialog again, this is why.

## Code style notes (beyond what ESLint enforces automatically)

- Indent is 4 spaces for `.ts` (the repo's `.editorconfig` default of 2 is overridden by ESLint's `@stylistic/js/indent` rule — ESLint wins).
- Private class members must be `_camelCase` (leading underscore required); private methods must **not** have a leading underscore.
- Explicit return types are required on all functions/methods (`allowExpressions: true` for arrow functions assigned inline).
- `curly: multi-or-nest` — single-statement `if`/`for` bodies should omit braces, consistently within a block.
